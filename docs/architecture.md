# System Architecture

This document describes the architectural layout and module structure of the **OpenMAD** Multi-Agent Orchestrator.

---

## 🗺️ Module Diagram

OpenMAD is designed as a decoupled, modular system written in Rust. The modules are grouped by core responsibilities:

```text
[ CLI Entrypoint (main.rs) ]
            │
            ▼
[ Orchestrator Core (orchestrator.rs) ]
   ├── [ DAG Planner (dag_planner.rs) ]
   ├── [ Agent Spawner (spawner.rs) ]
   │      └── [ Personas & Registry (agent.rs) ]
   ├── [ Model Router & APIs (model_router.rs) ]
   ├── [ Memory Engine (memory.rs) ]
   ├── [ Tool Router (tool_router.rs) ]
   └── [ Reflection System (reflection.rs) ]
```

---

## 🛠️ System Modules

### 1. Orchestrator Core (`orchestrator.rs`)
The central event engine. It initiates orchestration when given a user goal, runs the task evaluation loop, coordinates parallel work packages using `tokio::task::join_all`, and manages intermediate artifact persistence in the Shared Memory database.

### 2. DAG Planner (`dag_planner.rs`)
An implementation of a Directed Acyclic Graph (DAG) for agent workflows. It translates high-level task plans into nodes and dependency links. It performs topological sorting to determine the next executable ready task (where all dependency parents are marked `Completed`).

### 3. Agent Spawner & Registry (`spawner.rs`, `agent.rs`)
Responsible for managing agent identities.
- `agent.rs` defines `AgentPersona` (voice, titles, principles, system prompts) and registers defaults (John/PM, Mary/BA, Winston/Architect, Amelia/Coder, TestBot/Tester, Paige/Writer, Vivian/Vision).
- `spawner.rs` acts as a dynamic factory, assessing task scope to allocate channel-wrapped agent instances and garbage collecting them once tasks complete.

### 4. Model Router & Fallbacks (`model_router.rs`)
Handles connections to OpenAI, Anthropic, and Google Gemini API endpoints.
- Maps task types to optimal models.
- Houses **Fallback Chains** (`primary` $\rightarrow$ `secondary` $\rightarrow$ `fallback`). If a network or safety failure occurs, it transitions to the backup LLM.
- Tracks success/failure metrics in a thread-safe map, dynamically routing subsequent queries to the most successful provider.

### 5. Memory Engine (`memory.rs`)
Manages hierarchical context, agent core memories, and long-term semantic records.
- **Core Memory (RAM)**: Exposes `CoreMemory` representing agent-managed blocks (`persona` and `human` sections) that are dynamically formatted as XML and injected into LLM system prompts.
- **Persistent JSON Store**: Exposes `AgentMemoryStore` which writes modified core memories into `letta_memory_store.json` and loads them back on subsequent orchestrator launches.
- **Recall & Archival Memory (Cold Storage)**: Embeds inputs using `fastembed`'s text embedding models and implements a pure-Rust similarity scorer using **Cosine Similarity** to search historical task logs.
- **Shared Workspace**: Hosts `SharedAgentMemory` powered by a thread-safe `DashMap` for inter-agent artifact sharing.


### 6. Tool Router (`tool_router.rs`)
Coordinates system-level tools:
- Files reads and writes.
- Shell commands execution.
- Syntax AST parsing using `tree-sitter`. The tree-sitter parser parses source code blocks generated by Amelia, counting node frequencies to confirm syntax stability before submission.

### 7. Reflection System (`reflection.rs`)
Defines the quality review loop. It uses a Reviewer Agent persona to audit task outputs. If anomalies are found, it triggers a recursive **Self-Repair Loop** providing the agent with precise correction feedback.

---

## 🔄 Concurrency & Message Passing

OpenMAD uses a hybrid concurrency model:
- **Task Concurrency**: Non-dependent tasks in the DAG are scheduled onto independent async threads using Tokio's work-stealing scheduler.
- **Message Passing**: Inter-agent events are piped through multi-producer multi-consumer (MPMC) unbounded channels (`flume` and `crossbeam`) to allow agents to publish updates, log logs, or notify dependencies in real-time.
